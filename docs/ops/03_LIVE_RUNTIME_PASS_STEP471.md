# STEP471 — Live runtime pass (lists + dialog-flow)

Этот runbook нужен после deploy STEP471.

Цель:
- руками подтвердить, что после STEP470–471 списки и локальные dialog-flow читаются спокойно;
- отделить source-clean snapshot от реального Telegram runtime;
- не трогать accept/charge, если runtime-path уже проходит.

## 1) Creator-side

### 1.1 `📨 Мои заявки`
Путь:
- `📋 Меню` → `📨 Мои заявки`

Проверить:
- сверху только короткая шапка (`📨 Мои заявки`, summary, total, `стр N` только если pagination реальна)
- нет верхней текстовой портянки с повтором списка
- основной список только кнопками
- открытие карточки работает как раньше

### 1.2 `✉️ Диалог по заявке #...`
Путь:
- открыть принятую заявку

Проверить:
- карточка читается как локальный диалог по заявке
- `✍️ Ответить бренду` ведёт в input-mode экран
- `🪟 Открыть бренд` сохраняет локальный return-context

### 1.3 `✍️ Ответить бренду`
Путь:
- в диалоге нажать `✍️ Ответить бренду`
- отправить обычный текст в поле ввода Telegram

Проверить:
- после отправки бот возвращает в тот же `✉️ Диалог по заявке #...`
- видно `✅ Сообщение отправлено бренду`
- новое сообщение есть в истории
- нет выброса в generic menu

### 1.4 `📨 Заявки брендов`
Путь:
- `📋 Меню` → `📨 Заявки брендов`

Проверить:
- summary-only header
- нет верхнего текстового дубля
- filters / open-card работают как раньше

### 1.5 `📥 Inbox`
Путь:
- `📋 Меню` → `📥 Inbox`

Проверить:
- empty-state copy читается по-человечески
- нет `на странице 0`
- если Inbox пустой, пользователь понимает, что новый диалог появится, когда кто-то напишет первым

## 2) Brand-side

### 2.1 `📨 Заявки от креаторов`
Путь:
- `📋 Меню` → `📨 Заявки от креаторов`

Проверить:
- summary-only header
- нет верхней текстовой портянки
- filters / open-card / pagination работают как раньше

### 2.2 Accept → dialog loop
Путь:
- открыть новую заявку
- `✅ Принять`
- пройти post-accept flow

Проверить:
- accept проходит
- локальный контекст заявки сохраняется
- `📌 Стадия сделки` работает отдельно от диалога

### 2.3 Notice → dialog
Путь:
- дождаться нового сообщения от креатора
- открыть notice

Проверить:
- primary CTA = `💬 Диалог #...`
- открывается рабочий диалог по заявке
- `📌 Стадия сделки` остаётся отдельным соседним путём

## 3) Terminology pass

Проверить user-facing copy:
- вместо старой формулы `Интро = новый диалог` теперь везде активная формулировка `Новый диалог`
- paywall / credits / top-up / retry-notices говорят одинаково
- внутренние env/metric имена (`INTRO_*`, `mon.intro`) не влияют на UX copy

## 4) GO / NO-GO

### GO
- все списки читаются без дубля
- creator reply возвращает в тот же локальный диалог
- brand notice ведёт в `💬 Диалог #...`
- явных runtime surprises нет

### NO-GO
- любой send-path выбрасывает в generic menu
- любой list screen снова показывает текстовый дубль + кнопки
- old `Интро = новый диалог` всё ещё виден в активном UX
- local return-context ломается
