## 0) Ментальная модель системы

Collabka — это “**Transaction Router**” внутри Telegram:
- у людей есть **контекст** (канал, оффер, конкурс)
- у действий есть **переходы состояния**
- у финансов есть **атомарность**
- у качества есть **модерация и анти-абьюз**

Система строится на четырёх ядрах:
1) **Workspace** (канал как сущность)
2) **Giveaway** (конкурс как процесс)
3) **Marketplace** (оффер как продукт)
4) **Thread** (диалог как сделка)

Redis хранит **временное состояние**, Postgres — **истину**.

## 1) Архитектура (Woz: минимальная сложность)

### 1.1 Компоненты
- **Telegram Bot (grammy)** — UI и обработка событий
- **Vercel Serverless** — выполнение webhook и cron
- **Postgres (Neon)** — консистентные данные (истина)
- **Redis (Upstash)** — состояние/драфты/локи/TTL-кэш

### 1.2 Точки входа
- `POST /api/webhook` — единственный вход Telegram Updates
- `GET/POST /api/cron/giveaways-tick` — крон для завершения/розыгрышей
- `GET /api/dev-polling` — локальная разработка

### 1.3 Почему так
- **Serverless** убирает инфраструктурный шум.
- **Webhook-first**: минимальная задержка и правильная доставка.
- **Cron отдельно**: долгие операции (закрытие конкурсов, розыгрыш) не блокируют user-flow.

## 3) Принципы данных (Vitalik: прозрачность)

### 3.1 Истина: Postgres
Postgres хранит:
- пользователей, каналы, настройки
- конкурсы, участия, победителей
- офферы, треды, сообщения
- монетизацию, кредиты, планы
- модерацию и репорты
- верификацию

### 3.2 Состояние: Redis
Redis хранит:
- "ожидаемый ввод" (expectText)
- черновики (draft)
- активный workspace
- pay-session для Stars
- кэш eligibility
- локи cron

**Почему Redis, а не Postgres для драфтов:**
- драфты — временные, не должны засорять БД
- TTL и простое восстановление
- stateless-инстансы

## 4) Флоу №1 — Workspace (канал как объект)

### 4.1 Цель
Сделать канал “операционным объектом”:
- у него есть владелец
- у него есть настройки
- у него есть конкурсы и офферы

### 4.2 Как создаётся
**UI:** пользователь жмёт “Подключить канал” → бот просит forward поста.

**Технически:**
- Telegram message содержит `forward_from_chat` или `sender_chat`
- бот извлекает `chat_id`, `username`, `title`
- создаёт `workspaces`
- создаёт `workspace_settings`
- пишет `workspace_audit`

**Почему forward — лучший UX:**
- не нужны команды и ручные id
- меньше ошибок
- работает для любой аудитории

### 4.3 Логи и прозрачность
В `workspace_audit` пишется:
- кто создал
- когда
- какие важные настройки изменены

## 5) Флоу №2 — Giveaways (процесс “от идеи до итогов”)

### 5.1 Состояния конкурса
- `DRAFT` → `PUBLISHED` → `ENDED` → `DRAWN` → `RESULTS_PUBLISHED`

### 5.2 Почему стейт-машина
**Woz:** стейт-машина уменьшает баги, потому что:
- каждое действие валидно только в своём состоянии
- у нас явные переходы
- проще отлаживать и логировать

### 5.3 Draft wizard (Redis)
Создание конкурса — серия шагов:
- приз
- число победителей
- дедлайн
- спонсоры
- авто-настройки

Каждый шаг сохраняется в `draft:<tgId>`.

### 5.4 Проверка участия (eligibility)
**Что проверяем:** подписку на спонсоров.

**Как:** `getChatMember` для каждого sponsor chat_id.

**Кэш:** `elig_cache:<gwId>:<userId>:<chatId>` TTL 1–10 минут.

**Почему кэш:** Telegram API лимитирован, кэш уменьшает нагрузку.

### 5.5 Розыгрыш: детерминированность
Система использует seed + PRNG:
- seed строится из стабильных параметров
- PRNG даёт воспроизводимый результат

**Vitalik-принцип:** в audit сохраняем:
- `seedHash`
- `eligibleHash`
- размер пула

Чтобы можно было объяснить “почему так выбрало”.

### 5.6 Защита cron
Cron endpoint защищён `CRON_KEY`.
Cron также ставит Redis-lock, чтобы избежать двойного исполнения.

## 6) Флоу №3 — Marketplace (оффер как продукт)

### 6.1 Оффер
Оффер — это структурированное предложение:
- что даёшь / что хочешь
- формат (пост/сторис/обзор)
- гео
- контакты
- условия

### 6.2 Лента
Лента отдаёт офферы по:
- network_enabled воркспейса
- сортировка bump_at desc
- optional: featured placements

### 6.3 Bump
Bump — это легальный "ап" оффера.
Cooldown зависит от plan (free/pro).

**Почему bump_at:**
- без него лента становится статичной
- с ним рынок живой

---

## 7) Флоу №4 — Inbox Thread (сделка как объект)

### 7.1 Thread = контекст сделки
Thread создаётся при первом “Написать” по офферу.

Ключ:
- `unique (offer_id, buyer_user_id)`

Это предотвращает:
- дубликаты
- двойное списание credits

### 7.2 Сообщения
Все сообщения пишутся в `barter_messages`.

### 7.3 Закрытие
Thread можно закрыть (status CLOSED) без удаления истории.

---

## 8) Brand Pass (credits) — анти-спам дизайн

### 8.1 Проблема
Если бренды могут писать всем бесплатно — рынок тонет в спаме.

### 8.2 Решение
- credits списываются только при создании нового thread
- повторный вход в тот же thread бесплатный

### 8.3 Атомарность (Woz)
Списание credits и создание thread делаются в транзакции:
- если thread уже существует → не списываем
- если insert проиграл гонку → не списываем

**Это ключ к финансовой честности.**

---

## 9) Telegram Stars — платежи и безопасность

### 9.1 Pay-session
Перед invoice бот создаёт Redis pay-session:
- type покупки
- параметры
- order id

### 9.2 Successful payment
- читаем pay-session
- применяем изменения в DB
- удаляем pay-session

### 9.3 Почему так
- предотвращает “потерянные” оплаты
- позволяет обрабатывать разные покупки одним механизмом

## 10) Модерация (качество рынка)

### 10.1 Репорты
Пользователи могут жаловаться.

### 10.2 Очередь
Модератор видит OPEN репорты.

### 10.3 Действия
- freeze offer
- close thread
- resolve report

**Принцип:** модерация — это не банхаммер, это чистота рынка.

## 11) ✅ Верификация (feature-flag) — почему и как

### 11.1 Почему это важно
Верификация увеличивает доверие → рост конверсии.

### 11.2 Feature flag
`VERIFICATION_ENABLED=true|false`.

**Jobs:** выключено по умолчанию — чтобы не ломать прод.

### 11.3 Rolling safety
Если таблицы ещё нет, код использует fallback запросы.

### 11.4 UI
- меню “✅ Верификация”
- выбор kind
- заявка текстом
- статус PENDING

### 11.5 Mod flow
- очередь PENDING
- approve → ✅
- reject → причина

## 13) Инженерные гарантии (Woz)

### 13.1 Инварианты
- один thread на (offer, buyer)
- кредиты списываются только при создании нового thread
- giveaway winners уникальны
- миграции idempotent (IF NOT EXISTS)

### 13.2 Защита от двойного cron
- redis lock

## 14) Как расширять (правильный путь)

5) аудит логика
6) feature-flag если рискованно

### Пример расширения
- “deal stages” → добавить поле + UI + модку
- “proofs” → таблица + file_id + список
