# Collabka — контракт UI для выбора значений

## Назначение

Этот документ фиксирует единый UI-контракт для экранов, где пользователь **что-то выбирает**, а не просто переходит по меню.

Цель:
- сразу показывать текущее состояние,
- отделять **выбор** от **действий**,
- уменьшать путаницу,
- делать Telegram UI более app-like,
- сохранять компактность и edit-first поведение.

Это **не общий редизайн всего бота**, а стандарт именно для **selection surfaces**.

## Базовое правило

Разные типы экранов должны использовать **разный визуальный контракт**:

- **мультивыбор** → чекбоксная сетка
- **один выбор** → сетка с активной опцией
- **вкл/выкл** → toggle-контракт
- **действия и навигация** → обычные action-кнопки

Нельзя смешивать эти типы в одном блоке как будто это одно и то же.

---

## 1. Мультивыбор

Используется там, где пользователь может выбрать **несколько значений сразу**, и это состояние должно быть видно на экране.

Подходит для:
- категорий
- ниш
- языков
- форматов
- фильтров
- тематик
- scope selectors
- persistent profile pickers
- watchlist-подобных экранов

### Визуальный контракт

- выбрано → `☑️` или `✅`
- не выбрано → `⬜️` или `▫️`

### Правило

Нажатие по опции меняет состояние выбора и это должно сразу отражаться на том же экране.

Если выбор применяется **не сразу**, а после подтверждения, внизу нужен отдельный блок действий:
- `Сохранить`
- `Применить`
- `Очистить`
- `Назад`

Если выбор применяется **сразу**, не надо добавлять лишнюю кнопку `Сохранить`.

---

## 2. Один выбор

Используется там, где активным может быть **только одно значение**.

Подходит для:
- режима сортировки
- одного активного режима
- одного варианта выдачи
- шага wizard, где нужен ровно один выбор
- surface типа `Любой / конкретный вариант`

### Визуальный контракт

- активно → `🔘`
- не активно → `⚪️`

### Правило

Для single-choice нельзя использовать чекбоксы.
Пользователь должен сразу видеть:
- текущий активный вариант,
- остальные доступные варианты,
- структуру экрана.

Если выбор применяется мгновенно:
- `Сохранить` не нужен

Если нужен `Очистить`:
- он идёт **в нижнем action block**, а не внутри сетки опций

---

## 3. Вкл / Выкл

Используется там, где есть **одно бинарное состояние**:
- включено / выключено
- показывать / не показывать
- сеть включена / выключена
- уведомления включены / выключены

### Правило

Бинарный toggle:
- это **не чекбоксная сетка**
- это **не выбор одного значения из списка**

Состояние должно читаться как toggle, а не как picker.

---

## 4. Действия и навигация

Для действий и навигации нужны обычные action-кнопки.

Сюда относятся:
- `Сохранить`
- `Применить`
- `Очистить`
- `Обновить`
- `Назад`
- `Меню`
- `Домой`
- `Продолжить`
- `Опубликовать`
- `Удалить`
- `Подтвердить`
- `Принять`
- `Отклонить`
- `Открыть`
- `Разблокировать`
- действия со списанием, unlock, spend и т.д.

### Главное правило

Действия не должны визуально притворяться опциями выбора.
Навигация не должна визуально притворяться выбранным значением.

## Правила раскладки

## Парные ряды

Если рядом стоят короткие однотипные сущности, их обычно кладём **по 2 в ряд**.

Подходит для:
- коротких категорий
- фильтров одного типа
- соседних значений одного уровня

---

## Полноширинные строки

Одной строкой, full-width, даём:
- длинные подписи
- primary actions
- destructive actions
- рискованные действия
- редкие / особые варианты
- верхний `Любой`, если он работает как глобальный выбор

---

## Нижний блок действий

Отдельным нижним блоком выносим:
- `Сохранить`
- `Применить`
- `Очистить`
- `Сбросить`
- `Назад`
- `Меню`
- `Домой`

Эти кнопки не должны смешиваться с опциями выбора.

---

## Что пользователь должен видеть сразу

Любой экран выбора должен без угадывания показывать:
- что выбрано сейчас,
- что ещё можно выбрать,
- где именно происходит выбор,
- где находятся действия,
- применяется выбор сразу или после подтверждения.

Пользователь не должен гадать:
- активна ли уже эта опция,
- нужен ли `Сохранить`,
- что поменяется после нажатия.

---

## Семантика применения

У любого selection-экрана должен быть **один** из двух режимов.

## Мгновенное применение

Нажатие сразу меняет активное значение и применяет его.

Подходит для:
- простого single-choice
- лёгких фильтров
- быстрых переключателей режима

Правила:
- без `Сохранить`
- `Назад` остаётся только навигацией
- `Очистить`, если нужен, идёт внизу отдельной action-строкой

---

## Отложенное применение

Нажатие сначала меняет локальный state, а применение происходит после `Сохранить` / `Применить`.

Подходит для:
- мультивыбора
- больших фильтров
- экранов, где нежелательны случайные частичные изменения

Правила:
- `Сохранить` / `Применить` идут в нижнем блоке
- `Очистить` / `Сбросить` идут в нижнем блоке
- сетка опций остаётся сеткой опций

Нельзя смешивать мгновенное и отложенное применение в одном экране.

---

## Где этот контракт применять в Collabka

Применять там, где реально есть **выбор значений**, а не просто меню.

Хорошие кандидаты:
- фильтры каталога
- выбор категорий / ниш
- выбор языков
- выбор форматов
- выбор тематик
- audience / tag pickers
- persistent profile selectors
- scope selectors
- watchlist-подобные экраны

---

## Где этот контракт не нужен

Не тащим его в:
- обычные меню-хабы
- экраны действий
- destructive flows
- yes/no подтверждения
- `Принять / Отклонить`
- `Опубликовать`
- `Разблокировать`
- spend / unlock / purchase actions
- `Обновить / Назад / Меню / Домой`
- карточки статуса / receipt surfaces
- бинарные toggle-экраны

Ключевое правило:
- **selection ≠ action**
- **navigation ≠ selection**
- **toggle ≠ чекбоксная сетка**

---

## Антипаттерны

Нельзя:
- использовать чекбоксы для single-choice
- смешивать опции и действия в одной сетке
- ставить `Сохранить` внутрь блока опций
- делать `Назад` или `Меню` визуально похожими на selected-option
- использовать checkbox-grid для ON/OFF
- применять selection-стиль к destructive actions
- превращать любой экран в picker просто “для красоты”

---

## Правила текста

Helper-текст должен быть коротким.

Нормально:
- `Выберите один вариант`
- `Текущий выбор отмечен`
- `Можно выбрать несколько вариантов`

Не надо:
- длинных инструкций
- повторяющихся объяснений
- route-map текста
- “простыней” перед кнопками

---

## Telegram-правила для Collabka

Этот контракт должен сохранять текущие принципы Telegram UI в Collabka:
- edit-first single-surface
- явные `Назад / Меню / Домой`
- local context важнее guess-based navigation
- без тупиков
- без fake state markers на action-кнопках

---

## Acceptance checklist

Экран проходит контракт только если:

- правильно определён тип поверхности:
  - мультивыбор / один выбор / toggle / action surface
- state marker соответствует типу экрана
- options и actions визуально разделены
- парные ряды используются только для однотипных соседних опций
- длинные и рискованные действия вынесены отдельно
- `Сохранить / Очистить / Назад` стоят в нижнем action block
- семантика применения понятна и едина
- пользователь сразу видит текущий state
- `Назад / Меню / Домой` остаются навигацией, а не “выбором”
- на не-selection экранах нет лишнего checkbox/radio шума

---

## Короткая форма стандарта

Использовать в проекте как краткое правило:

- мультивыбор → чекбоксная сетка
- один выбор → сетка с активной опцией
- вкл/выкл → toggle-контракт
- короткие соседние опции → обычно по 2 в ряд
- длинные / primary / destructive действия → отдельной строкой
- `Сохранить / Очистить / Назад / Меню / Домой` → отдельный нижний блок действий
- выбор ≠ действие
- навигация ≠ выбор
- toggle ≠ чекбоксная сетка
