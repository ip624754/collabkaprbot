# 20 — Security review notes: fail‑open vs монетизация (2026-02-24)

**Контекст:** в феврале 2026 мы получили внешний разбор про риски “fail‑open” архитектуры для монетизации Telegram‑бота.
Этот документ фиксирует **что из критики принимаем**, **что уже усилено в коде**, и **какие принципы считаем инвариантами** для Collabka PR (@collabkaprbot).

> Source of truth по текущей реализации: `docs/00_CURRENT_STATE.md` + код.

---

## 1) Главное правило: fail‑open только для UX, но не для денег

### Допустимый fail‑open
- `/api/health` — должен отвечать даже при деградации Redis/DB (иначе мониторинг слепой).
- `/start` role-gate (`ui_mode` в Redis) — если Redis недоступен, не блокируем пользователя: показываем безопасную развилку или ведём “как раньше”.

### Недопустимый fail‑open
- Любые действия, которые:
  1) **списывают кредиты/деньги**, или
  2) открывают **платный доступ** (контакты/публикации), или
  3) меняют **критичный статус** (publish/ended/expire)

Для этих зон при деградациях используем **fail‑safe** (останавливаемся/ставим ORPHANED/требуем ручного решения) либо переносим “истину” в DB.

## 2) Paid-unlock контактов (Brand Pass): защита от double-charge при деградации Redis

**Риск из рецензии:** если unlock держится только в Redis (TTL), при его деградации пользователь может:
- повторно нажать “🔓 Контакты” и получить повторное списание,
- либо получить непредсказуемое состояние (unlock “то есть, то нет”).

**Что сделано:** unlock стал **exactly-once** на стороне Postgres.
- Таблица: `brand_contact_unlocks(brand_user_id, workspace_id, unlocked_until)` (см. миграцию `migrations/026_brand_contact_unlocks.sql`).
- Механика:
  - Redis остаётся быстрым кешем/UX.
  - Если Redis недоступен, проверяем unlock через DB.
  - Активация unlock + списание кредитов выполняются **атомарно** (transaction + advisory lock), поэтому повторный клик в TTL **не списывает второй раз**.

Сопутствующие меры:
- анти‑bypass текста профиля (де‑линкификация `@/t.me/http/email` до unlock)
- после списания выдаём “контакт‑пакет” отдельным сообщением, чтобы ценность была очевидна

## 3) Payments (Telegram Stars): hardening против неверных счетов/сумм

**Риск из рецензии:** неправильная обработка `invoice_payload`/суммы может привести к:
- неверному начислению продукта,
- применению оплаты “не туда”,
- ручному apply ошибочного платежа.

**Что сделано (defense‑in‑depth):**
- На `pre_checkout_query` валидируем **`invoice_payload + total_amount + currency`** до подтверждения оплаты.
- На `successful_payment` делаем повторную валидацию (ретраи/edge cases).
- Если проверка не проходит → статус **ORPHANED** + OPS алерт.
- Fallback apply (cron/админка) и ручной Apply в админке **блокируются**, если сумма/валюта не совпадают с ожидаемыми для продукта.

> Примечание: “подмена payload пользователем” в Telegram модели не является основным вектором, но проверка суммы/валюты и схемы payload защищает от ошибок интеграции и от неконсистентного auto-heal.

---

## 4) Access control: ownership проверяем в SQL (safe-getters)

**Риск из рецензии:** паттерн “достали сущность по id → потом проверили права” легко ломается и иногда даёт:
- side‑effects до проверки,
- разный тайминг/ошибки,
- или реальную дыру, если где-то забыли guard.

**Что сделано:** для чувствительных сущностей используем **ownership в SQL**.
- Лиды/заявки:
  - `db.getBrandLeadForActor(leadId, actorUserId)`
  - `db.getBrandApplicationForActor(appId, actorUserId)`
- Роутер callback’ов теперь опирается на safe-getters.
- Опасные действия по лидам (assign/soft-delete) дополнительно ограничены ролями `owner/curator/admin`.
- Покупка размещения в офиц.канале (`a:off_buy`) получает оффер через `db.getBarterOfferForOwner(ownerUserId, offerId)`.

---

## 5) Deep-links и пересылка

**Принцип:**
- Публичные deep-links (витрина/публичные страницы) могут пересылаться свободно.
- Приватные сущности (тред/лид/заявка/внутренние действия) должны быть защищены **ownership‑проверкой** (DB).

Мы не делаем “session-binding для всего” (это ломает UX пересылки), но всё приватное/платное не открывается без права.

---

## 6) Что можно усилить дальше (backlog, по желанию)

1) **Invoice payload подпись (HMAC)** как дополнительный контракт (defense‑in‑depth) поверх проверки суммы/валюты.
2) Расширить safe-getters на все сущности, которые открываются по `id` из callback/deeplink.
3) Метрика в `/api/health`: счётчики `payments.validation_failed` и `unlock.db_fallback` (Redis-only), чтобы видеть деградации.

---

## TL;DR
- Fail‑open оставляем для UX и наблюдаемости.
- Для монетизации и приватных действий: DB‑истина + atomic guards + ownership‑в‑SQL.
